Architecture

How the factory is built

The "solid foundation", not vibe-coding

Five layers, each depending only downward. A country (jurisdiction) and a trade (vertical) are orthogonal — so covering N countries × M trades costs N + M, never N × M. Adding Germany later is a new pack, not an edit to the core.

PluginsSandboxed, contract-tested escape hatch for genuinely bespoke logicfuture
Tenant configData only — branding, price lists, series, users. Customisation is data, never a fork✓ built
Vertical packsTrade knowledge — construction / reformas: mediciones, partidas, terminology✓ built
Jurisdiction packsCountry law — es-ES: IVA, IRPF, invoice chaining — effective-dated✓ built
CapabilitiesQuoting, billing… define ports. Zero country / trade knowledge✓ built
KernelTenancy, money, effective-dating, composition, persistence, events✓ built
▲ depends downward only — enforced in CI · the kernel & capabilities contain no IVA, no partida, no country anything

The tenant spec picks the packs; the resolver binds adapters to ports and fails loudly at resolve time on any conflict or gap — never in front of a customer.

Time is a dimension of correctness

Tax rules resolve by date, not version: amending a March invoice in November applies March's law. Every decision is stored with its justification — legal basis, inputs, rule id — on the invoice, never recomputed.

Boundaries are enforced, not aspirational. A build-time linter fails CI if a capability imports a country pack, if one pack imports another, or if a forbidden literal (a tax name, a rate like 0.21, a hardcoded locale) leaks into the core. It already caught — and we fixed — a real leak on its first run.
The falsifiable test (proven, runs in CI): boot the kernel + billing with no country pack loaded and it must fail loudly — no tax rate can exist without a jurisdiction. If it ever "worked", Spain would have leaked into the core. It fails, exactly as required.
